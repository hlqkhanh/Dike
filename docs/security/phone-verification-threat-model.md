# Stage 3 phone verification and role threats

| Threat                                                  | Control                                                                                                                                      | Remaining limitation                                                                      |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| OTP brute force and replay                              | Random six-digit code, keyed HMAC, constant-time comparison, challenge/session/phone binding, five attempts, TTL and single-use finalization | Redis and HMAC keys remain sensitive operational assets                                   |
| SMS pumping                                             | Atomic user/phone/session/IP hourly and daily limits, cooldown, no fail-open path                                                            | Real provider and global cost budget are blocked on S3-PILOT-01                           |
| Concurrent verification and phone takeover              | Mongo partial unique verified-phone index, transactional recheck of phone version and active challenge ID                                    | Operational handling of conflicts must not merge accounts                                 |
| Crash after provider approval or database commit        | Persisted approval state, challenge idempotency record, append-only audit in the same Mongo transaction                                      | Redis retention is bounded; expired approval metadata eventually requires a new challenge |
| SIM swap or recycled number                             | No account linking/merging by phone; phone change invalidates verification and effective elevated privileges                                 | Phone possession does not prove identity; eKYC and account recovery are later stages      |
| Role escalation through a stale session/browser payload | Effective roles derived from the current database user on every authorization check; no role claims in session cookies                       | All future protected modules must use the guard/service                                   |
| Last admin removal race                                 | Shared authorization revision write serializes grants/revokes, phone changes and verification                                                | Direct database maintenance must preserve the invariant                                   |
| Development bypass in hosted environments               | Reject fake provider, exposed code and phone bypass; disabled provider makes readiness unavailable                                           | Production adapter is intentionally absent                                                |
| Credential/PII leakage                                  | No plaintext OTP or phone in Redis/Mongo/audit, sensitive logger fields redacted, BFF no-store, disabled browser capture                     | Developers must not record or manually share local OTP screens                            |

The role CLI is a privileged operations tool. Possession of database credentials already grants substantial authority; restrict access to the operations host, retain independent operator identity logs, and use ticket references for audit reasons. The actor argument is audit context, not a substitute for authenticating the human operator.
